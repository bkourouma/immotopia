# Audit de sécurité du 9 novembre 2026

## Synthèse pour le propriétaire du produit

- Nous avons passé l'application au crible, sans rien modifier, sur quatre sujets : connexion et configuration, séparation entre agences, fichiers et paiement, site web et serveurs.
- Résultat : aucune faille « critique », mais 7 failles graves (« élevées ») et 16 moyennes, plus 25 faibles. Les plus sérieuses : un fichier piégé déposé sur un bien pouvait attaquer les visiteurs ; une agence pouvait rattacher un bien d'une autre agence ; un gestionnaire pouvait se nommer administrateur ; le compte super-administrateur du site de test était connu et visible.
- Presque tout ce qui relève du code est corrigé dans cette PR, sans changement de base de données (donc sans migration).
- Une contre-vérification indépendante (« contre-audit », 5 relectures adversariales) a ensuite relu les correctifs eux-mêmes. Elle a trouvé 2 failles élevées, dont une **introduite par cette PR** (un garde anti-falsification de requête qu'une adresse très longue pouvait ralentir jusqu'à bloquer l'API), 12 moyennes et une vingtaine de faibles. Toutes les élevées et la plupart des autres sont corrigées dans cette même PR (section 8).
- Vous devez agir vous-même sur une douzaine de points (section 6) : changer le mot de passe du super-administrateur du site de test et le fermer au public, activer la revue obligatoire sur GitHub, poser une protection HTTPS dans les serveurs, changer une clé Twilio exposée, lancer sur les serveurs les deux scripts d'inventaire (fichiers suspects, liaisons entre agences), relire les fichiers de configuration réels, valider la construction des images Docker en Node 22.
- Restent différés : la double authentification (MFA), la refonte de l'inscription, plusieurs mises à jour de bibliothèques qui changent de version majeure, le passage de la garde d'isolation en mode bloquant et celui de la politique de sécurité du navigateur (CSP) en mode bloquant.
- Plusieurs règles métier ont été choisies par prudence : elles sont à valider (section 4, H1 à H29).

## 1. Périmètre et méthode

- Base auditée : `origin/main` au commit `aa857a25`, le 2026-11-09.
- Quatre territoires audités en lecture seule :
  1. authentification et configuration ;
  2. isolation entre agences et portails ;
  3. fichiers, paiement, injection, IA ;
  4. front, infrastructure, dépendances.
- Correctifs ensuite livrés en 7 lots sur une branche d'intégration (`orch/2026-11-09-audit-securite`), sans migration de schéma : lot 1 (connexion, sessions, journaux, CSRF), lot 2 (fichiers téléversés, DOCX), lot 3 (isolation, droits), lot 4 (configuration, paiement, e-mail), lot 5 (front), lot 6 (infrastructure, CI, dépendances, graines de données), lot 7 (reliquats, traductions, classeur des fonctionnalités, documentation).
- Les lots 1, 2, 3, 4 et 6 ont été relus par un vérificateur indépendant (certains deux fois, avec des allers-retours de corrections) ; les lots 5 et 7 l'ont été par le superviseur ; une vérification finale indépendante couvre l'assemblage.
- Le 2026-11-10, cinq contre-audits adversariaux (section 8) ont relu la PR entière ; leurs constats ont été corrigés par cinq agents sur des territoires de fichiers disjoints (commit `377cd363`), puis une seconde vague a traité les reliquats de code et cette documentation.
- Vérifications d'ensemble : après la vague du contre-audit, `tsc --noEmit` sans erreur sur l'API et le web, et Jest API sur les suites touchées (135 suites passées, 3 sautées, 0 échec, 2587 tests). Avant elle, la suite API complète avait été exécutée par lots (une exécution unique saturait la mémoire à 4 Go). La suite web complète n'a pas été menée à terme (sous-ensembles ciblés verts). La CI de la PR a révélé un test d'isolation faux (rôle de test sans `PROPERTIES_CREATE`), corrigé (`0c8ef6a3`) et rejoué sur une base PostgreSQL jetable pour les cas TEN-01 et TEN-02 seulement.
- Les statuts du tableau ont été recoupés avec le code de la branche pour chaque note.

## 8. Contre-audit Opus (5 relectures adversariales)

### Méthode

Le 2026-11-10, cinq relectures adversariales indépendantes (modèle Opus, effort élevé, lecture seule) ont repris la PR complète sur cinq territoires : AUTH (connexion, sessions, CSRF, limiteurs), FILES (DOCX, uploads), TEN (membres, invitations, permissions, isolation), PAY/INFRA (paiement, e-mail, tâches planifiées, Compose, seeds, nginx) et FRONT + DOC (interface, puis exactitude de ce rapport et des documents d'exploitation). Chaque relecture cherchait à contourner les correctifs eux-mêmes (expressions régulières pathologiques, courses, cas limites des nouvelles gardes) et à contredire chaque affirmation de la documentation par le code. Les correctifs ont ensuite été faits par cinq agents (A à E) sur des territoires de fichiers disjoints, chacun avec un test qui échoue sans le correctif, puis vérifiés ensemble (`tsc` API et web sans erreur, 135 suites Jest passées).

### Synthèse

- **2 élevés**, tous deux corrigés : un déni de service par expression régulière dans le garde CSRF, **régression introduite par cette PR** (exécuté sans authentification, avant le limiteur global) ; un déni de service par expression régulière dans l'extraction des balises d'un modèle DOCX (un fichier de 5 Ko pouvait figer l'API).
- **12 moyens** : 10 corrigés ; 2 signalés (comptes de démonstration du bundle staging, prérequis de la CSP bloquante). Un moyen était aussi une régression de la PR (la révocation de sessions pouvait être esquivée, CA-TEN-1).
- **23 faibles distincts** (24 relevés, dont un doublon) : 20 corrigés, 3 signalés ; plus 2 constats hors du diff et 1 remarque, signalés.
- **15 inexactitudes de documentation** (B1 à B8, I1 à I7) : toutes corrigées dans ce rapport et dans `SECURITY.md`, `RUNBOOK.md`, `DEPLOIEMENT.md`, `PLAN_DEPLOIEMENT_PRODUCTION.md`.
