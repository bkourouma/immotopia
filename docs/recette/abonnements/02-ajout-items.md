# Recette abonnements — S2 Ajout d'items (extensions)

Écrit le 2026-11-09, **non rejoué** (scénario rédigé d'après la lecture du code ; aucun navigateur lancé). Cadre, matrice de couverture et écarts consolidés : voir `README.md` de ce dossier. La souscription initiale, l'essai et la première facture sont en `01-souscription.md` (renvois par identifiant, par exemple `S1-16`).

Périmètre : les six extensions réellement présentes dans le code (`EXT_LOTS_10`, `EXT_COPRO`, `EXT_CHANTIER`, `EXT_BIENS_10`, `EXT_INVENTAIRE_WHATSAPP`, `EXT_SIGNATURES_SUPPLEMENTAIRES`, `packages/api/src/lib/subscription/catalog.ts:64-73`), leur prix selon les packs détenus et les paliers, l'ajout hors essai (prorata) et pendant l'essai, le rattachement à un pack, les retraits (à l'échéance, partiel, immédiat avec motif), le prix figé et les refus. Côté agence : page « Mon compte › Abonnement » (il n'existe pas de menu « Paramètres › Abonnement ») et fichier `packages/api/src/services/subscription-admin-extras-service.ts`. Côté super-admin : fiche agence › onglet « Abonnement ».

## Réalité de l'environnement

- Instances de recette : `SUBSCRIPTION_ENFORCEMENT=enforce`, paiement en ligne plateforme en mode `SIMULATOR`, e-mails captés localement, cache des droits d'agence de 30 s (recharger la page de l'agence après une action du super-admin ; l'API invalide pourtant le cache de son propre processus à chaque écriture, `packages/api/src/services/subscription-v2-service.ts:368-371`, `:839`). Sources : `docs/recette/packs/CADRE_COMMUN.md` §2.
- **Il n'existe aucun achat direct d'extension par l'agence.** L'agence consulte les offres (`GET /api/tenants/:tenantId/subscription/extension-offers`) et envoie une demande (`POST …/extension-requests`) ; seul le super-admin ajoute l'extension (`POST /api/admin/tenants/:tenantId/subscription/items`). Voir `E-S2-1`. Les cas « côté agence » (S2-01, S2-02) couvrent donc la consultation et la demande, et les cas d'ajout (S2-04 et suivants) se jouent par le super-admin.
- Le prix d'un ajout ne dépend pas de `SUBSCRIPTION_ENFORCEMENT` (`warn` et `off` ne changent ni prix, ni prorata, ni plafond d'achat) ; ces réglages jouent seulement sur les gardes de quota (hors périmètre ; voir la section quotas). Le plafond **acheté** augmente dès l'ajout ; le refus à la limite (409 `QUOTA_EXCEEDED`) n'est pas rejoué ici.
- La tâche planifiée `packages/api/src/jobs/subscription-usage-job.ts` n'est pas déclenchable depuis l'interface. Elle est nécessaire pour : terminer un retrait programmé à l'échéance (élément `ENDED`, démarrage d'un reste `SCHEDULED`, `applyDueItemTransitionsTx`) et émettre la facture de la période suivante qui reprend les lignes de prorata. Provocation : attendre le passage de 02:30 UTC **après** la fin de période, ou un développeur appelle `triggerSubscriptionUsageCycle({ now, tenantId })` (`jobs/subscription-usage-job.ts:628`, `now` simule une date). Aucun bouton n'existe pour cela.
- Pas d'interface pour : la modification du catalogue (`PATCH /api/admin/catalog/:code`), le retrait partiel (`quantity` du `DELETE …/items/:itemId`), le choix explicite du pack parent (`parentItemId`). Ces pas sont marqués « API seule ».
- Le prix et la vendabilité de `EXT_SIGNATURES_SUPPLEMENTAIRES` dépendent de l'état du catalogue de la base : 5 000 FCFA vendable après `npm run db:seed:catalog`, mais 0 FCFA **non vendable** si seule la migration est passée (voir `H-S2-1`). Le premier geste de la section est de lire `GET /api/admin/catalog`.
- Les modifications de catalogue du cas S2-20 touchent un état partagé : relever les valeurs avant, les **restaurer** après.
- Aucun mot de passe n'est écrit ici ; le super-admin est celui du seed `packages/api/prisma/seeds/create-super-admin.ts`.
