> **Non rejoué.** Ces documents sont **écrits, non rejoués** : aucun navigateur n'a été lancé, aucun scénario n'a été exécuté dans l'interface ni sur une base. Chaque résultat attendu a été déduit en **lisant le code** (références `fichier:ligne` dans la colonne « Source » de chaque cas) et chaque montant a été recalculé à la main d'après le catalogue. Ce dossier est le scénario de test de la **gestion des abonnements, souscriptions et changements de pack** d'ImmoTopia : souscription d'une agence, ajout d'items (extensions) à un abonnement, passage d'un pack à un autre (Agence, puis ajout du Syndic, puis Opérateur intégré, retour arrière), capacités et dépassements, cycle de vie (impayé, grâce, lecture seule, réactivation), actions du super-administrateur, droits et isolation entre agences, cas limites. Il complète — sans les remplacer — [`docs/recette/packs/`](../packs/CADRE_COMMUN.md) (recette module par module de chaque pack), [`SCENARIO_SYNDIC_ABONNEMENT.md`](../SCENARIO_SYNDIC_ABONNEMENT.md) (un seul pack Syndic) et [`operateur-integre/09-abonnement-quotas.md`](../operateur-integre/09-abonnement-quotas.md).

Référence de règles : [`docs/architecture/PLAN-ABONNEMENTS.md`](../../architecture/PLAN-ABONNEMENTS.md) (**lorsque le code et le plan divergent, ces documents suivent le code** et consignent l'écart), catalogue `packages/api/src/lib/subscription/catalog.ts` (`DEFAULT_CATALOG`), calculs `packages/api/src/lib/subscription/pricing.ts`.

## 2. Cadre

### 2.1 Réalité de l'environnement (reprise de `docs/recette/packs/CADRE_COMMUN.md`)

Ces points décrivent les instances de recette ; ce ne sont pas des anomalies.

- `SUBSCRIPTION_ENFORCEMENT=enforce` : menus masqués et routes refusées pour un module non souscrit, quotas bloquants selon la politique de l'agence. Avec `warn` (défaut de l'API) tout reste visible et aucun quota ne bloque ; avec `off` rien n'est contrôlé. Les cas qui dépendent du mode le disent.
- Paiement en ligne de la plateforme en mode `SIMULATOR` ; e-mails captés par un récepteur local (rien ne part) ; ne **jamais** cliquer « Payer en ligne » sur une instance dont le prestataire est en mode réel.
- Cache des droits d'agence de 30 s : attendre 30 s après une action du super-administrateur (un rechargement immédiat renvoie l'ancienne valeur ; `?fresh=1` ne rafraîchit pas ce cache).
- La tâche planifiée `packages/api/src/jobs/subscription-usage-job.ts` (passage complet à 02:30 UTC, alertes à :15 chaque heure) n'est pas déclenchable depuis l'interface : chaque cas qui en dépend indique comment la provoquer (appel par un développeur, décalage de dates en base présenté comme préparation de données, ou attente).
- La création d'une agence donne toujours un **essai de 30 jours** : l'état « abonnement ACTIVE, période réglée » ne s'obtient pas par clics seuls ; les cas qui le demandent le préparent (paiement simulé après fin d'essai, ou préparation de données).
- Seul **un** bouton de changement de pack existe dans l'interface (Patrimoine) ; les autres changements de pack passent par l'API et sont marqués « API seule » (voir l'écart du même nom au §5).

### 2.2 Conventions des cas

- Identifiant `S<section>-<nn>` ; chaque cas = tableau « Champ / Contenu » (objectif, rôle, priorité, packs, préconditions) puis tableau d'étapes `# / Action dans l'interface / Résultat attendu / Source`, puis « Vérification API/base » si utile.
- Priorités : **P1** bloquant (parcours impossible, montant faux, fuite entre agences, droit incorrect), **P2** important, **P3** confort.
- Montants en FCFA entiers, HT sauf mention ; TVA 18 % calculée sur le total HT et arrondie à l'unité (`packages/api/src/lib/subscription/pricing.ts:366-380`) ; prorata = `round(montant × jours restants / jours de la période)`, jour d'ajout compris (`pricing.ts:281-285`) ; annuel = 11 mensualités.
- « API seule » : geste sans écran, à jouer par `curl` avec le cookie du compte concerné ; « développeur » : geste réservé à qui peut lancer la tâche ou lire la base.
- Données fictives : e-mails `@exemple.test`, agences « Recette Abonnements … ». Aucun mot de passe ni secret n'est écrit : le super-administrateur est celui du seed `packages/api/prisma/seeds/create-super-admin.ts`, les mots de passe des comptes créés sont des valeurs de test choisies à l'exécution et restent hors du dépôt.

### 2.3 Rôles utilisés

| Rôle                           | Ce qu'il fait dans ces scénarios                                                                                                                                                                        |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Super-administrateur           | crée les agences, ajoute/retire packs et extensions, dérogations, remises, catalogue, avoirs, factures plateforme, lecture seule manuelle (`PLATFORM_SUBSCRIPTIONS_VIEW/EDIT`, `PLATFORM_MODULES_EDIT`) |
| TENANT_ADMIN                   | lit l'abonnement et les factures de son agence, paie en ligne, envoie une demande d'extension (`TENANT_SETTINGS_EDIT`)                                                                                  |
| Gestionnaire, comptable, agent | lecture seule ou refus selon la permission (détail et matrice route × rôle : section S7)                                                                                                                |
| Tâche planifiée                | transitions d'échéance, factures de période, relevés, alertes, rappels (aucun acteur humain)                                                                                                            |

### 2.4 Jeux de données de départ

Chaque fichier de section commence par son tableau « Jeu de données de départ » (agences jumelles par cas pour qu'un cas ne perturbe pas un autre : par exemple `Alpha-FR`, `Bravo` en S3). Le jeu de données du **fil rouge** (§4) est indépendant et se joue sur une agence dédiée.

### 2.5 Vérification mécanique

`npx prettier --check docs/recette/abonnements` depuis le worktree. Aucun test applicatif n'est concerné (documentation seule).

**Calendrier de référence (UTC).** Création le 2026-11-09 à 10:00 ; si l'exécution a lieu un autre jour, recalculer les dates et les prorata avec les formules du §2.2 (les mois utilisés ont 31 puis 28 jours : voir S3-03, S8-15 et S8-17 pour les autres longueurs). ## 7. Limites de ce lot

- **Non rejoué** : aucun attendu n'a été vu à l'écran ; les libellés d'interface, les montants et les statuts viennent du code et de calculs à la main. Les rares points non confirmables par le code sont signalés « à confirmer au rejeu » dans leur cas (par exemple le rendu arabe et le défilement à 375 px en S8, la résiliation avec renouvellement à zéro en S5-17).
- Les courses (S4-10, S8-02, S8-04 à S8-06, S8-11, S8-12) sont déduites de la lecture des verrous ; leur rejeu demande des requêtes parallèles scriptées, indiquées dans chaque cas.
- Les cas qui dépendent de l'horloge utilisent un décalage de dates en base (préparation de données) ou le déclenchement de la tâche par un développeur : l'option `now` de `runSubscriptionUsageCycle` ne simule proprement que l'avenir (S5, « Réalité de l'environnement »).
- Valeurs provisoires du catalogue (packs Particulier, `EXT_SIGNATURES_SUPPLEMENTAIRES` à 5 000 seulement après `db:seed:catalog`) : les montants attendus supposent un catalogue en base aligné sur `DEFAULT_CATALOG` ; vérifier `GET /api/admin/catalog` avant de commencer.
- La proposition d'évolutions du module d'abonnement est dans un autre document (`docs/architecture/PROPOSITIONS-ABONNEMENTS.md`, autre lot) ; ce dossier ne la préjuge pas.
