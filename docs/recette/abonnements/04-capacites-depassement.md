# Recette abonnements — S4 Capacités, dépassement et alertes

Écrit le 2026-11-09, **non rejoué**. Cadre, matrice des sections et écarts consolidés : voir [README.md](README.md).

Cette section vérifie les jauges (LOTS, COPROPRIETES, CHANTIERS, BIENS_DETENUS, ACTIFS, PHOTOS_INVENTAIRE, SIGNATURES_MENSUELLES), la réserve unique, ce qui compte comme un lot, le registre `LotActivation`, les alertes 80 % / 100 %, la politique de dépassement (`BLOCK`, `BILL_OVERAGE`, `WARN_ONLY`) et les montants de dépassement facturés. Les chemins sont relatifs au dépôt ; les numéros de ligne ont été relus le 2026-11-09.

## Réalité de l'environnement

- **Mode** : les instances de recette tournent en `SUBSCRIPTION_ENFORCEMENT=enforce`, paiement en ligne de la plateforme en `SIMULATOR`, e-mails captés par un récepteur local, aucun WhatsApp (`docs/recette/packs/CADRE_COMMUN.md:48-53`). Le comportement `warn` / `off` n'est donc **pas rejouable** sur ces instances ; il est décrit en S4-23.
- **Cache des droits : 30 s** (`packages/api/src/services/subscription-v2-service.ts:364`, `:422`). Toute écriture faite par le service (dérogation, extension, politique) invalide le cache de l'API (`:1268`) ; une écriture SQL ou un script lancé hors du processus API ne l'invalide pas : attendre 30 s puis recharger la page.
- **Tâche planifiée** `packages/api/src/jobs/subscription-usage-job.ts` : passage complet chaque jour à **02:30 UTC** (relevés, échéance, factures, rappels, alertes) et **alertes seules** chaque heure à :15 (`:610-618`). **Aucun bouton** dans l'interface. Pour chaque cas qui en dépend, la recette indique comment la provoquer : (a) attendre le passage réel ; (b) un développeur appelle `runSubscriptionUsageCycle({ tenantId, now?, alertsOnly? })` (`:531-584`, ou `triggerSubscriptionUsageCycle` `:628`). `alertsOnly: true` ne fait ni relevé ni facturation (`:553-577`). La tâche ne traite que les abonnements `TRIALING`, `ACTIVE` ou `PAST_DUE` (`:58-62`, `:535-538`). Quand un cas passe `now` dans le futur, la date d'émission des factures reste celle de l'horloge réelle (`packages/api/src/services/platform-invoice-service.ts:667`).
- **Registre des lots** : toujours tenu, quel que soit le mode ; seul le refus dépend du mode (`packages/api/src/services/lot-registry-service.ts:568-573`).
- **Volumes** : les exemples du plan (100 à 320 lots) ne se saisissent pas à la main. Les cas S4-19 et S4-20 exigent une **préparation par script développeur** (création en masse de biens ou de lots). Les autres cas utilisent un **jeu réduit** obtenu par dérogation négative (onglet « Abonnement » > bouton « Accorder une dérogation », champ « Quantité (négative pour retirer) », `apps/web/src/components/admin/tenant-detail/SubscriptionTab.tsx:306`) : la dérogation abaisse `limit` (`packages/api/src/lib/subscription/entitlements.ts:172-180`) et les montants de dépassement se calculent sur `limit + 1…`.
- **Dates** : toutes en UTC, « aujourd'hui de référence » = **2026-11-09**. Si la recette est jouée un autre jour, décaler **toutes** les dates du même nombre de jours.
- **Destinataires des alertes** : administrateurs actifs de l'agence (rôle `TENANT_ADMIN`), sinon e-mail de contact de l'agence ; plus tous les super-admins actifs, sauf pour un espace `PARTICULIER` (`packages/api/src/jobs/subscription-usage-job.ts:115-141`, `:167-180`).
