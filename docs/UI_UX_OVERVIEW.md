# ImmoTopia — Overview UI / UX de toutes les pages

> État des lieux **descriptif** de l'interface telle qu'elle existe aujourd'hui dans `apps/web`.
> Ce document ne propose pas de refonte : il décrit ce qui est réellement implémenté, page par page,
> avec l'UI (composants, mise en page) et l'UX (parcours, états, interactions, frictions constatées).
>
> Branche analysée : `fix/securite-semaine-1` · 110+ écrans · Périmètre : `apps/web/src/pages` + layouts/composants associés.

## 1. Socle technique de l'interface

| Élément                    | Réalité actuelle                                                                                                                                   |
| -------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| Framework                  | React 18 + React Router v6 (`BrowserRouter`), build Vite 6                                                                                         |
| Bibliothèque UI principale | **Ant Design 5** (`Layout`, `Menu`, `Table`, `Form`, `Card`, `Modal`, `Descriptions`, `Statistic`, `Steps`, `Tabs`…)                               |
| Bibliothèque UI secondaire | **Tailwind CSS 3** + un mini design-system maison façon shadcn/ui dans `components/ui/` (Radix : `select`, `dropdown-menu`, `checkbox`, `tabs`…)   |
| Icônes                     | `@ant-design/icons` **et** `lucide-react` selon les pages                                                                                          |
| Graphiques                 | Recharts (dashboard CRM, patrimoine)                                                                                                               |
| Typographie                | **Inter** (Google Fonts, poids 300→900), fallback système                                                                                          |
| Couleur primaire           | `#3b82f6` (Tailwind `primary`) côté Tailwind, `#1890ff` (bleu AntD par défaut) côté AntD — **deux bleus coexistent**                               |
| Fond applicatif            | `bg-slate-50` (`#f8fafc`) ; cartes blanches                                                                                                        |
| Sidebar                    | Fond `#0f172a` (slate-900), thème `dark` AntD, séparateur `#1e293b`                                                                                |
| Thème sombre               | **Aucun** (`dark:` absent de toute la codebase)                                                                                                    |
| Internationalisation       | **Aucune** (pas de `i18n`/`useTranslation`) — textes FR en dur, `ConfigProvider` sans `locale`                                                     |
| Chargement des routes      | `React.lazy` + `Suspense` par chunk (`properties`, `crm`, `rental`, `syndics`, `admin`, `owner-portal`…) avec un `<Spin size="large">` plein écran |
| Garde-fous                 | `ErrorBoundary` global, `ProtectedRoute` (auth + rôle + appartenance tenant)                                                                       |

### Point structurant : deux design systems cohabitent

Environ **80 % des pages sont 100 % Ant Design** (look bleu AntD, `Card`+`Table`+`Form`), et **une quinzaine sont en Tailwind/shadcn** (look slate, boutons custom, `lucide-react`) : `Register`, `VerifyEmail`, `AuthCallback`, `Properties` (racine), `properties/PropertyPublic*`, `properties/PropertySearch`, `crm/Deals`, `crm/DealFormPage`, `admin/TenantDetail`, `admin/AdminCollaboratorDetail`, `admin/AdminInviteCollaborator`.
Quelques pages sont **hybrides** (AntD + Tailwind dans le même écran) : `properties/Properties`, `rental/Installments`, `rental/Payments`, `rental/Documents`, `rental/Penalties`, `crm/Calendar`.

Conséquence UX : ombres, rayons, hauteurs de champs, styles de boutons et de badges changent d'un écran à l'autre au sein d'un même parcours.

## 2. Les quatre coquilles (shells) de l'application

### 2.1 `DashboardLayout` — back-office (composants `dashboard/`)

- **Sidebar fixe 256 px** à gauche (`position: fixed`, `z-index: 30`), fond slate-900, logo « ImmoPro / Gestion Immobilière » (bloc bleu 40×40 + icône maison).
- **Header sticky 64 px** blanc : bouton burger (mobile uniquement), champ de recherche global, sélecteur de langue « FR », avatar + nom + rôle avec menu déroulant (Profil / Paramètres / Déconnexion, cette dernière en `danger`).
- **Zone de contenu** : `overflow-y-auto`, fond slate-50, padding responsive `px-4 sm:px-6 lg:px-8 py-4`, `Suspense` interne avec spinner « Chargement… ».
- **Responsive** : bascule à `min-width: 1024px` via `useMediaQuery`. En dessous, la sidebar devient un `Drawer` gauche de 256 px ; le menu se referme automatiquement après navigation.
- ⚠️ Le **champ de recherche du header n'a aucun handler** (`onChange`/`onSearch` absents) : il est purement décoratif. Idem pour le bouton « FR ».
- ⚠️ L'entrée de menu « Paramètres » pointe vers `/settings`, qui redirige vers `/settings/profile` — c'est-à-dire exactement la même page que « Profil ».

### 2.2 `TenantPortal/Layout` — portail locataire

Même charte (sidebar 256 px slate-900, header partagé), sous-titre « **Portail Locataire** ». Menu plat de 6 entrées : Tableau de bord, Mon bail, Paiements, Dépôt de garantie, Maintenance, Documents. Redirection défensive : un `clientType === 'OWNER'` est renvoyé vers `/owner`, tout autre type vers `/dashboard`.

### 2.3 `OwnerPortal/Layout` — portail propriétaire

Même charte, sous-titre « Portail Propriétaire ». Menu plat de 11 entrées : Tableau de bord, Mes propriétés, Baux, Revenus, Échéances, Paiements, Dépôts de garantie, Maintenance, Documents, Rapports, Préférences.

### 2.4 Pages « nues » (sans shell)

`Login`, `Register`, `ForgotPassword`, `ResetPassword`, `VerifyEmail`, `AuthCallback`, `auth/AcceptInvitePage`, `newsletter/{Subscribe,Confirm,Unsubscribe}` : carte centrée sur fond dégradé/clair, aucune navigation. Ce sont les seules routes publiques.

## 3. Navigation : trois arborescences selon le profil

La sidebar (`components/dashboard/sidebar.tsx`, 729 lignes) calcule le profil à partir de `user.globalRole`, `tenantMembership` et `tenantClient`, puis sert **un des trois menus** :

| Profil                           | Menu servi                                                                                                                                                    |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `SUPER_ADMIN`                    | **2 entrées** : Tableau de bord · Administration (Tenants, Rôles & Permissions, Statistiques, Journaux d'audit)                                               |
| Collaborateur de tenant          | **11 groupes** : Tableau de bord, Gestion, Propriétés, Patrimoine, Syndic, Clients, Transactions, Rapports, CRM, Gestion Locative, Maintenance, Communication |
| Utilisateur public (sans tenant) | **2 entrées** : Tableau de bord · Propriétés (Toutes / Catégories)                                                                                            |

**Particularité UX intéressante** : le groupe « Syndic » est **contextuel**. Les 12 sous-entrées (Fiche syndic, Lots, Charges, AG, Prestataires, Documents, Finances, Recouvrement, Comptabilité, Budgets, Profils & incidents) pointent vers la dernière copropriété consultée, mémorisée dans `localStorage` sous `last-syndic:<tenantId>`. Sans copropriété active, elles retombent sur la liste avec un paramètre `?openSyndicSection=…`.

**Frictions relevées :**

- Le surlignage de l'élément actif repose sur un algorithme maison de normalisation d'URL (UUID → `:id`, tentative de match exact puis préfixe). Il est fragile sur les routes imbriquées.
- Le menu public propose `/properties/categories` — **cette route n'existe pas** dans `App.tsx` (404 silencieux via redirection).
- Le groupe « Propriétés » du menu tenant contient « Ajouter une propriété » : une **action** placée au même niveau que des **destinations**.
- Idem pour « Nouveau bail », « Nouveau contact », « Nouveau ticket » — le menu mélange navigation et création.
- Aucun fil d'Ariane (breadcrumb) nulle part, alors que la profondeur atteint 4 niveaux (`/tenant/:id/syndics/:id/lots/:id/compte`).

## 5. Patterns transverses observés

### 5.1 États de chargement (4 conventions coexistent)

1. `<Spin size="large">` plein écran, centré — routes lazy, la majorité des pages AntD.
2. `<Card loading>` — skeleton natif AntD (`Dashboard`), la meilleure des quatre : pas de saut de mise en page.
3. `<Table loading>` — spinner intégré au tableau.
4. Spinner Tailwind maison (`animate-spin rounded-full border-b-2 border-blue-600`) — `DashboardLayout`, `ProtectedRoute`, pages TW.

Aucun **skeleton de contenu** générique n'est utilisé ailleurs que dans `Dashboard` ; ailleurs, le contenu apparaît d'un bloc.

### 5.2 États d'erreur

- Standard : `<Alert type="error" showIcon>` en haut de page, parfois avec une action « Réessayer » (`Dashboard`, `InviteCollaborator`).
- Accès refusé : `ProtectedRoute` affiche un écran plein « **Accès refusé** » (3 variantes : rôle insuffisant, mauvais tenant, aucun tenant) — texte seul, **sans bouton de retour ni lien de sortie**. L'utilisateur est bloqué et doit utiliser le menu.
- ⚠️ `alert()` natif dans `PropertySearch`/`PropertyPublic`, `console.error` silencieux ailleurs.
- Un `ErrorBoundary` global couvre les crashs de rendu.

### 5.3 États vides

Très bien couverts : `<Empty>` AntD présent sur la quasi-totalité des listes, souvent avec une description contextuelle et un bouton d'action (« Commencez par créer votre première propriété »). C'est un point fort constant de l'application.

### 5.4 Retours d'action

- `message.success` / `message.error` AntD dans **46 pages** — toast en haut de l'écran, cohérent.
- 1 seule page utilise `notification.*`.
- Confirmations : `Popconfirm` AntD dans les pages AntD ; **`window.confirm()` natif** dans 4 fichiers (`admin/AdminCollaboratorDetail` ×3, `admin/TenantDetail` ×2, `rental/Installments`, `rental/Penalties`) — dialogue système qui casse la charte.

### 5.5 Formulaires

- Pages AntD : `Form layout="vertical"` + `rules` déclaratives, messages sous les champs, `Input.Password`, `Select`, `DatePicker`.
- Pages TW : state React manuel + erreurs affichées à la main.
- Deux wizards (`PropertyFormWizard` 6 étapes, `LeaseFormWizard` 5 étapes adaptatives) avec `Steps` AntD, validation par étape et retour ciblé sur l'étape en erreur.
- Aucun garde-fou « modifications non enregistrées » : quitter un formulaire long perd la saisie sans avertissement (le brouillon du wizard propriété est l'exception).

### 5.6 Tableaux et listes

`Table` AntD partout dans le back-office, colonnes en français, statuts en `Tag` colorés, actions en fin de ligne avec `Tooltip`. La pagination est tantôt le composant `Pagination` séparé, tantôt celle intégrée à `Table` — deux rendus différents selon les pages. Sur mobile, seul `SyndicLots` bénéficie d'un traitement de scroll horizontal dédié (`.lot-table` dans `index.css`) ; les autres tableaux larges débordent sans aide visuelle.

### 5.7 Responsive

- Point de rupture unique : **1024 px** (`useMediaQuery('(min-width: 1024px)')`), utilisé pour basculer sidebar ↔ `Drawer`.
- Grilles AntD en `xs=24 sm=12 lg=6/8/12`, grilles Tailwind en `sm:grid-cols-2 lg:grid-cols-3`.
- Le header masque le burger au-delà de 1024 px et le champ de recherche est plafonné à 400 px.
- Pas de traitement tablette spécifique entre 768 et 1024 px.

### 5.8 Accessibilité

- **10 occurrences de `aria-label`** dans toute la codebase (dont le fallback de route, correctement doté de `role="status"` et `aria-live="polite"`).
- Pas de gestion du focus à l'ouverture/fermeture des modales au-delà du comportement natif AntD.
- Pas de `skip link`, pas de repères ARIA (`role="navigation"`, `role="main"`).
- Contraste : texte `slate-600` sur `slate-50` et `#94a3b8` sur `#0f172a` (sous-titre de la sidebar) sont à vérifier au regard du ratio AA.
- Les icônes-boutons d'action de tableau reposent sur `Tooltip` (survol) : sans équivalent accessible au clavier/lecteur d'écran.

## 6. Synthèse : ce qui fonctionne, ce qui accroche

### Points forts

1. **États vides systématiquement traités**, souvent avec une action de sortie.
2. **Deux wizards intelligents** : validation par étape, étapes conditionnelles selon le type d'opération, retour automatique sur l'étape fautive, brouillon possible.
3. **Dashboard CRM** : filtres persistés dans l'URL, KPI cliquables qui pilotent tout l'écran, workbench orienté action.
4. **Sidebar contextuelle du module Syndic** avec mémorisation de la dernière copropriété.
5. **Vocabulaire métier français homogène** et statuts normalisés en `Tag` colorés d'un module à l'autre.
6. **Circuit déclaration de paiement (locataire) → validation (gestionnaire)** cohérent des deux côtés.
7. **Journal d'audit lisible** : payload technique traduit en libellés métier.
8. **Permissions rendues honnêtement** sur le dashboard (`—` au lieu de `0`).
9. Code-splitting par module : le temps de chargement initial reste contenu malgré 110+ écrans.
